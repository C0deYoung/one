# 郧西一中 Blender + Unreal Engine 5 实施计划

**Goal:** 制作可在 Windows 电脑独立运行、依据历史照片还原的第一人称校园探索互动游戏。

**Architecture:** Blender 制作建筑与道具，FBX 输送几何、碰撞和 UV，UE5 重建材质、组织场景并实现玩法。先完成主楼入口样板，再扩展校园；旧 Three.js 项目作为玩法和资料参考，不直接转换其粗模作为最终资产。

**Tech Stack:** Blender、Unreal Engine 5、FBX、PBR、Lumen、Blueprint、Enhanced Input、UMG、SaveGame、Git LFS。具体软件版本在样板导入和打包验证后锁定。

## 1. 范围与前提

- 首版：Windows 单机、键鼠第一人称、校园主要室外区域、一段可行走外廊、一间可进入教室、七个回忆点、存档、暂停和画质设置。
- 首版白天为基准；黄昏/晚自习在室外样板性能达标后加入。
- 全楼室内、NPC 人群、多人联机、移动端、动态天气归入后续版本。
- 还原年代待确定；暂按老校园历史风貌组织资料，不混用不同时期的改造。
- 分布图 v2 是布局起点，不是有精确尺寸的测绘图。问号位置、层数冲突、校门样式均进入待核实表，不默认为事实。
- 工期是熟练单人全职工作的估算，不含学习软件、等待资料与大规模返工；完成样板后重新估算。

## 2. 已有资料与迁移边界

- 素材目录：`E:/download/pic/一中/`，包括建筑照片、分布图 v2、照片位置匹配表。
- 旧项目：`js/buildings.js`、`js/world.js` 用于查找物体与布局线索；其中估计尺寸不作为测量结果。
- `js/memories.js`、`js/controls.js`、`js/audio.js` 用于梳理互动、输入与声音需求，逻辑在 UE 中重建。

- README、DESIGN 与分布图存在版本差异，以证据表和后续确认形成统一依据。

## 4. 分阶段工作与验收

### 阶段 A：资料定版与开发环境（2–3 人日）

1. 检查 CPU、GPU/显存、内存、磁盘、Blender/UE 安装情况；选定实际测试电脑。
2. 建立照片资产表：编号、建筑、年代、视角、可见结构、遮挡、可信度、缺失信息。
3. 对照照片位置匹配表与分布图 v2，记录校门、篮球场、连廊、食堂等冲突。
4. 建立统一坐标与尺寸表；区分实测、用户确认、照片估计。争议区域先用可替换体块。
5. 建立工程与备份，记录软件版本。此阶段不以购买插件作为前置条件。

交付：资料索引、统一布局草案、未知项清单、环境记录。
验收：每栋主要建筑能追溯到照片；年代与布局冲突有明确标记。

### 阶段 B：全校园体块与导入样例（3–5 人日）

1. Blender 按米建模，制作 1 米立方体和门洞测试件，导入 UE 后验证为 100 厘米。
2. 锁定导出缩放、轴向、法线、枢轴、命名和重新导入流程。
3. 根据布局建立校园体块，校准主楼长宽高、庭院和连廊关系；地图比例仍是估计的部分保持标记。
4. UE 创建第一人称角色和基础碰撞，贯通校门—广场—主楼—连廊路径。
5. 配置对应参考照片的固定相机；首次生成 Windows 测试包。

交付：体块校园、导入规范、可运行测试包。
验收：玩家尺度自然；通路可走；俯视布局符合统一草案；无 100 倍缩放错误；脱离编辑器可以启动。

### 阶段 C：主楼入口可玩样板（8–12 人日）

范围：绿玻璃入口、两侧各一段教学楼外廊、入口台阶及前方少量广场。

1. 以 01/05/07/09 及 10/13/26/27/31 等资料核对主楼与外廊，确认不同照片的朝向与年代。
2. 完成幕墙轮廓、包边、分格、校徽、立体校名、雨棚、柱子和台阶。
3. 制作可复用的窗框、墙段、栏杆、外廊和空调模块；窗口、走廊需有真实深度。
4. 校正照片透视，提取可用局部纹理；去掉明显照片阴影、遮挡和重复透视。整张仰拍照片不充当入口几何。
5. 输出颜色、法线、粗糙度等贴图，在 UE 中建立瓷砖、玻璃、金属和混凝土主材质与实例。
6. 设置中性日光与 Lumen，先校准曝光和材质，再做气氛；增加少量有照片依据的植物。
7. 加入一个回忆点，跑通交互提示、打开照片、关闭并恢复行走。
8. 导出正面、斜侧、近景、玩家视角截图，并与照片同视角比较。

交付：精细样板、模块资产、四组对比图、可玩包。
验收：楼层与可见窗格数量对应参考；主楼轮廓与入口比例无明显偏差；侧面仍有正确体积；墙面不带整张照片的树影/人像；门洞与台阶可走。未知尺寸不声明为测量精度。
质量门槛：样板还原度未通过对比复核，不批量扩建；依据样板实测成本修订后续工期。

### 阶段 D：主要室外校园（12–20 人日）

1. 扩展五层教学楼与相连外廊。
2. 完成教师办公楼、科技实验楼、连接走廊与具有辨识度的楼梯/红色门架。
3. 完成宿舍、食堂和高一教学楼外观；资料不足的区域保留待核实标记。
4. 制作广场、左右花园、凉亭、水池、球场、车棚和校园边界，逐项核对布局证据。
5. 布置树木、灌木与远山，优先准确的树种轮廓、尺寸和位置。
6. 为远景/普通物件设置 LOD 或适用的 Nanite，重复物体采用实例；同时检查碰撞与视线遮挡。

交付：全校园主要外景、更新后的照片对照记录。
验收：主要路线连通，辨识性建筑逐栋对照通过；首人称与俯视都成立；无根据的美化不覆盖已有证据。

### 阶段 E：探索玩法与代表性室内（5–8 人日）

1. 建立 BP_CampusCharacter、BPI_Interactable、BP_MemoryPoint、WBP_MemoryViewer 与 SG_CampusProgress。
2. 使用数据资产/数据表管理七个回忆的 ID、标题、文字、照片与关联地点。
3. 用视线检测与距离限制交互，避免穿墙触发；支持已收集回忆重看。
4. 实现移动、疾跑、暂停、提示、存档/读档、完成反馈与音量/画质设置。
5. 制作一间参考照片支持的教室以及到达它的走廊/楼梯；不默认复制开放整栋楼。
6. 加入脚步、校园环境声与上下课铃；在性能允许时完成黄昏/晚自习预设。

交付：完整探索流程、代表教室、声音与存档。
验收：七个点均可触发且不重复计数；重启恢复进度；UI 打开时角色不误移动；关闭 UI 后输入恢复；新游戏与继续游戏均可完成。

### 阶段 F：性能、还原复查与交付（4–7 人日）

1. 在阶段 A 选定电脑上记录 GPU、CPU、显存占用、分辨率与画质，测试完整路线及主楼/花园/夜景重负载位置。
2. 暂以 1080p、目标画质 60 FPS 为目标；这是待实测目标，不是对所有电脑的承诺。记录平均值、1% low 和明显卡顿。
3. 根据 GPU/CPU 实测瓶颈调整植物、透明玻璃、阴影、材质、纹理驻留与加载；不把 Nanite 视为自动解决所有性能问题。
4. 检查所有照片匹配镜头、日夜曝光、穿模、楼梯、地图边界和卡住点。
5. 输出 Windows Shipping 包，在不依赖项目编辑器的环境验证启动、存档、退出和再进入。
6. 整理源工程、Blender 文件、资产清单、操作说明和已知资料缺口。

交付：Windows 可玩版本、源资产、验收截图、性能记录与已知问题清单。
验收：完整流程可通关，主路线无阻断；无丢材质/缺文件；约 20 分钟连续游玩无崩溃；性能报告明确测试条件。

## 5. 美术与技术约定

- 建筑按楼栋和可复用模块拆分，UE 组织校园；避免单一超大网格。
- FBX 传递网格/UV/碰撞，Blender 复杂着色节点不假定自动转换；最终效果在 UE 材质中验证。
- 自定义凸碰撞使用 UCX 命名并独立检查，门洞、楼梯和连廊单独验证。
- 优先平铺材质和饰边纹理；普通资产从 1K–2K 起步，关键资产按屏幕占用决定是否 4K，避免全校园统一大贴图。
- 玻璃采用照片对应的颜色、粗糙度与反射，不默认所有绿色幕墙都高度透明。
- Lumen 作为高画质路线；先测目标硬件，再决定低画质光照方案。Nanite 按网格类型和版本支持选择。
- 摄影测量不是当前零散老照片的前置流程；若能补拍，可用来补充局部资产。生成式图片不得充当真实结构证据。
- 首版采用简单地图组织；有实测需求再引入复杂流送、World Partition 或额外框架。

## 6. 工期与决策节点

合计约 34–55 人日，即熟练单人全职约 7–11 周；资料补齐、学习、反馈等待另计。优先完成 A–C，约 13–20 人日得到能够判断还原度的可玩样板，而不是仅有静态效果图。

必须尽早解决：还原年代、关键布局冲突、实际目标电脑、开放室内范围。没有答案时可继续资料整理与模块测试；争议建筑不能当作最终还原定版。
